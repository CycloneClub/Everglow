## Summary

Reviewed the Phase 1 changes against the phase base: 44 C# item classes under
`Sources/Modules/Yggdrasil/KelpCurtain/Items/`, seven offline PowerShell gates
under the phase `scripts/` directory, and the reconciled `01-INVENTORY.json` /
`evidence/*.xml` artifacts they operate on.

The C# side is in good shape. Every value/rarity/recipe/category edit I could
trace matches the committed Feishu evidence rows (spot-checked `HuskburstBullet`,
`ActivatedDogStaff`, `ThornTurtleShell`, `BladeOfGreenMoss`, `GreenSungloStaff`,
`MeatLantern`, `RazorbeakBow`, `MossySpell`, the three RedAlgae items, `ArcI`,
`JadeFruit`, and the four DevilHeart recipes against their `<tr>` rows). The
`buyPrice`/`sellPrice` convention was corrected in the right direction
(`Item.sellPrice` is 5x `Item.buyPrice`; assigning the design 价格 via
`buyPrice` is correct). No binary/art asset was added or modified; no BOM/CRLF
violations were found in the changed text files. The C# findings are limited to
pre-existing dead constants.

The gates all run and reproduce the documented results (validate 103 entries,
reconciliation 103, tranche-A 38/38, tranche-B 20/20, parser fixture PASSED).
The strict localization gate is red (45/58) but this is an explicitly recorded
user-directed deferral, not a defect introduced here.

The substantive defects are in the tooling: the parser's default output
silently destroys the reconciliation it is meant to sit alongside, and the
tranche no-placeholder guard does not actually see untracked placeholder PNGs.
There is also a real data-quality defect where the parser's category heuristic
mislabels weapons as armor and vice-versa.

## Critical Issues

### CR-01: Parser's default output silently overwrites the reconciled inventory

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/parse-design-xml.ps1:75-76` (write at `:488-491`)
**Issue:** `parse-design-xml.ps1` defaults `-OutJson` to the live
`01-INVENTORY.json` and writes a fresh base parse that contains only the fields
it generates. Re-running it (the natural action after refreshing a design
snapshot — and the very workflow the plan describes) silently destroys all of
the reconciliation added by plans 02–05. I verified this non-destructively by
running the parser with `-OutJson`/`-OutMd` pointed at temp files and diffing
against the live artifact:

| Field | Live `01-INVENTORY.json` | Regenerated |
| --- | --- | --- |
| `internal_name` populated | 60 | 0 |
| `tranche` A/B populated | 82 / 20 | 0 / 0 |
| `labels[]` | 5 | 0 |
| `assumptions[]` | 7 | 0 |
| `deviations[]` | 38 | (top-level key absent) |
| `phase1_actions[]` | 11 | (top-level key absent) |

This is a data-loss risk with a very large blast radius (the entire reconciled
inventory plus the deviation ledger mirror), and there is no `-Force`, backup,
or merge guard. `01-VERIFICATION.md` treats the JSON as the machine source of
truth, so this regression could be committed unnoticed.
**Fix:** Require an explicit opt-in before overwriting the default path, or make
regeneration merge instead of replace. Minimal guard:

```powershell
# near the default assignment (~line 75)
if (-not $OutJson) { $OutJson = Join-Path $phaseDir '01-INVENTORY.json' }
if ((Test-Path -LiteralPath $OutJson) -and -not $Force) {
	throw "refusing to overwrite $OutJson (reconciliation data would be lost); pass -Force or a different -OutJson"
}
```

and add `[switch]$Force` to the `param()` block. A stronger option is to emit
the parsed base to `01-INVENTORY.raw.json` and have the reconciliation step
merge into the committed file.

## Warnings

### WR-01: `check-tranche-A/B` no-placeholder guard cannot see untracked placeholder PNGs

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/check-tranche-A.ps1:88-96` (identical in `check-tranche-B.ps1:88-96`)
**Issue:** Two independent false-negatives:
1. The guard parses `git status --porcelain` with the default untracked-file
   mode (`-unormal`), which collapses an entirely untracked directory to a
   single `?? path/to/dir/` entry. `$path -like '*.png'` is then false, so a new
   folder full of placeholder art is never flagged. I reproduced this in a
   throwaway git repo:
   - `git status --porcelain` → `?? Sources/.../Items/`
   - `git status --porcelain -uall` → `?? Sources/.../Items/NewArt/placeholder.png`
2. The guard only inspects the **working tree**. The phase's own art changes are
   committed, so `git status` reports nothing for them. The gate as written can
   never enforce the "0 binary/art changes in the phase" property that
   `01-05-SUMMARY.md` claims it verifies (that assertion was actually made with
   a separate `git diff` command that is not part of any gate).
**Fix:** Add `-uall` and also assert against the committed phase range, e.g.:

```powershell
$statusLines = & git -C $repoRoot -c core.quotepath=false status --porcelain -uall -- $itemsRel
# plus a committed-range check for the same guarantee:
$addedPng = & git -C $repoRoot diff --name-only --diff-filter=AM ``
	gsd-plan-head-before-01-01..HEAD -- "$itemsRel/*.png"
```

### WR-02: Inventory `category` misclassifies weapons as armor and armor as weapons

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/parse-design-xml.ps1:245-258` (`Get-Category`)
**Issue:** `Get-Category` tests `RE_ARMOR` (`护具|套装效果`) before `RE_WEAPON`
(`伤害|击退|暴击|使用时间`), and `RE_ARMOR` matches the generic `护具` header of
the mixed "魔心铁" table `TK7ddgDgMosNN8xzvs1cS0H0nBH`
(headers `护具|贴图|代码|数值|价格|稀有度|效果|套装效果`). Every row in that
table is therefore `armor`, including five weapons in `01-INVENTORY.json`:

- `item-armor-devil-heart-gun` → `Items.Weapons.DevilHeart.DevilHeartGun`
- `item-armor-devil-heart-staff` → `...DevilHeartStaff`
- `item-armor-devil-heart-gyroscope` → `...DevilHeartGyroscope`
- `item-armor-devil-heart-bayonet` → `...DevilHeartBayonet` (a melee sword)
- `item-armor-devil-heart-bow` → `...DevilHeartBow`

The inverse also occurs: the Ruin armor pieces are labelled
`weapons.summon` (`item-weapons.summon-ruin-mask`,
`item-weapons.summon-ruin-magic-rob`, `item-weapons.summon-ruin-leggings`),
because their table headers contain `伤害`/`召唤`. The result is eight
internally inconsistent classifications, a wrong Weapons/Armor grouping in
`01-INVENTORY.md`, and an inflated `weapons` count in the `validate-inventory`
summary line.
**Fix:** Prefer the row's weapon-evidence over the generic equipment header —
e.g. classify as `weapons.<sub>` when the row text carries a damage-class token
(`Melee`/`Ma`/`S`/`Range`/`召`) or when the table exposes weapon stat columns,
and only fall back to `armor` otherwise. Alternatively key the section off the
table's preceding heading rather than the `护具` header token.

### WR-03: `validate-inventory.ps1` does not return its documented exit code 3 for a missing JSON

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/validate-inventory.ps1:50-53`
**Issue:** The script sets `$ErrorActionPreference = 'Stop'` (line 44) and then
calls `Write-Error "inventory JSON not found: $JsonPath"` followed by
`exit 3`. Under `Stop`, `Write-Error` raises a terminating error, so the script
aborts before `exit 3` and a caller sees a generic failure/exception rather than
the documented code 3. Verified by invoking with a nonexistent `-JsonPath`: the
error propagated and `exit 3` was never reached (the header documents `3` for
this branch at lines 8-10).
**Fix:** Use a non-terminating write, matching the other gates:

```powershell
Write-Output "FAIL: inventory JSON not found: $JsonPath"
exit 3
```

### IN-02: `feishu.row_color` can bleed across rowspan cells

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/parse-design-xml.ps1:230-243` (`Get-RowColor`) with `:357-360`
**Issue:** `$rowCells` is built from every grid key matching `^$r,`, which
includes rowspan cells carried down from earlier rows. The evidence data
contains 12 `rowspan` cells (e.g. a `rowspan="4"` green effect cell in the
DevilHeart table), so a row can inherit `row_color` from a merged cell above it.
`row_color` is informational only — status is derived from the checkboxes — so
this does not affect gate outcomes, but the recorded value can be misleading.
**Fix:** For `Get-RowColor`, only count cells whose owning `<tr>` is the current
row (track the originating row index in `Get-LogicalGrid`).

### IN-03: Entry IDs contain non-ASCII CJK characters

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/parse-design-xml.ps1:221-228` (`ConvertTo-Slug`)
**Issue:** `ConvertTo-Slug` preserves `\u4e00-\u9fff`, so 52 of the 103 entry
IDs embed Chinese (e.g. `item-weapons.misc-青须手杖`,
`item-weapons.misc-绿琉璃果`). These are used as stable identifiers and echoed
by all gates; on a console using the ANSI code page they render as mojibake
(observed for `GreenSungloStaff` during localization-gate output), which makes
CI logs and diffs hard to read and can complicate tooling that assumes ASCII.
**Fix:** Transliterate/romanize fallback slugs to ASCII (e.g. keep the
`row-$r` / numeric fallback, or derive a hash when `name_en` is empty) and store
the CJK only in `name_zh`.

### IN-06: Tranche coverage counts any blocker as "implemented"

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/check-tranche-A.ps1:76-79` (same in `check-tranche-B.ps1:76-79`)
**Issue:** The predicate treats any blocker other than the exact
`no repo implementation found` marker as coverage. The parser stamps
`design artwork not complete ...` / `design code not complete ...` blockers on
rows with unchecked boxes, so a phase-1 `artwork_complete == true` entry with no
class file could pass the gate purely because its code checkbox is false. No
current entry relies on this (I confirmed every selected entry resolves to a
tracked `.cs`), so this is latent, but it weakens the gate's stated guarantee.
**Fix:** Exclude the parser-generated checkbox blockers from the "covering"
set, or require `$hasClass` for entries that are not explicitly `no repo`.

### IN-07: Parser assumes the evidence wrapper and default XML resolution

**File:** `.planning/phases/01-item-inventory-completed-art-items/scripts/parse-design-xml.ps1:294-303`
**Issue:** `$x.LoadXml("<root>$raw</root>")` requires the snapshot to have no XML
declaration/DOCTYPE, and `XmlDocument` is created without setting
`XmlResolver = $null`. Both are safe for the committed, trusted `<fragment>`
snapshots (first bytes verified: `<fragment mode="full" ...`), so this is
defensive only — a future snapshot exported with a prolog would throw.
**Fix:** Strip a leading declaration before wrapping, and set
`$x.XmlResolver = $null` explicitly.
