# Phase 1 Plan 01 — Inventory Pipeline Tracer: Evidence Snapshot to One-Category Inventory

## User Story

**As a** Kelp Curtain maintainer, **I want to** turn the three authoritative Feishu design documents into a committed, machine-readable item inventory, **so that** every later phase can implement and audit items against a single reusable source of truth.

> Planner-derived from the ROADMAP Phase 1 `Goal` line (the roadmap goal is not authored in user-story form; this restates it without adding scope).

<objective>
Prove the entire inventory pipeline end-to-end on one real slice: fetch the three Feishu design documents as XML with block IDs and checkbox state, run a deterministic parser that turns the item document's weapons table into a JSON entry set, emit the matching Markdown matrix, and gate it with an offline validator — before any expansion to all categories.

Purpose: this is the tracer for Phase 1. It exercises fetch -> committed evidence -> parse -> JSON -> Markdown -> validation on the thinnest real path, so an architectural dead-end (unreadable XML, lost block IDs, flipped checkbox columns) is caught after one commit instead of after a hundred transcribed rows. D-01/D-02/D-03 (inventory artifact shape) and D-08/D-09 (one-time snapshot + committed evidence) are implemented here.

Output: `evidence/{biology,item,terrain}.xml`, `scripts/parse-design-xml.ps1`, `scripts/validate-inventory.ps1`, `01-INVENTORY.json` (weapons slice), `01-INVENTORY.md` (weapons section), `COVERAGE.md`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Feishu doc -> lark-cli | External, private document content crosses into the repo as XML; content is attacker-influenceable by anyone who can edit the design docs. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering/Elevation | Fetched Feishu XML consumed by the parser/agent | high | mitigate | Treat all fetched content as data: the parser only reads table cells and checkbox/`background-color` attributes; it never executes or follows text found in cells. The `must_haves.truths` backstop records the data-only rule. |
| T-01-02 | Information Disclosure | lark-cli token / auth cache | high | mitigate | Fetch with `--jq ".data.document.content"` so only DocxXML is written; never commit tokens, JSON envelopes, or auth files; the prohibitions block records the rule. |
| T-01-03 | Denial of Service | Oversized/malformed XML parse | medium | mitigate | Parse table-by-table from the committed snapshot; the fixture test bounds parser behaviour; evidence is a committed local file, not a live stream. |
| T-01-04 | Repudiation/Tampering | Silent mutation of the authoritative design source | high | mitigate | Phase 1 issues no `docs +update`; only `docs +fetch` is used, and the read-only prohibition is recorded. |
| T-01-05 | Tampering | Unsafe generated filenames/paths from document text | low | accept | Evidence filenames are fixed literals (`biology.xml`, `item.xml`, `terrain.xml`); parser output goes to two fixed planning paths. No path is derived from document text, so the residual risk is accepted. |
| T-01-SC | Tampering | Package/CLI supply chain | low | accept | No packages are installed in this phase; lark-cli 1.0.95 is already installed and versioned (RESEARCH §"Environment Availability"). No install task exists, so no legitimacy checkpoint is required. |
